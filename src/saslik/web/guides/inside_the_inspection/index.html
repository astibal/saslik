01

On the path

The app chooses a destination. Routing adds Saslik.

More details · about what you see

  • Transparent to configuration

    The app does not need a proxy address or a proxy menu. Routing and interception rules put Smithproxy on the connection path. Transparent does not mean undetectable: TLS inspection changes the certificate the app sees.

  • Routing and interception are different jobs

    Routing gets traffic to the workspace. Its interception rules deliver selected traffic to the proxy. In Saslik, Linux TPROXY is part of that plumbing; not every packet is automatically inspected.

  • Keep the destination, change the path

    The app still asks for its intended server. Smithproxy retains the destination information and handles the onward connection. The diagrams use a simple HTTPS connection; other protocols can behave differently.

02

Two TLS links

TLS inspection creates two encrypted connections.

More details · about what you see

  • Not one TLS connection with a window cut into it

    Smithproxy participates in two separate TLS sessions with separate keys. It acts as the server toward the app and as the client toward the destination. Replies follow the same arrangement in reverse.

  • Inspection is a configured choice

    This diagram describes an intercepted TLS connection. A connection that is passed through without TLS interception does not expose its encrypted application content to these tools.

  • Server validation still matters

    Trusting the workspace CA on the client does not establish the real server’s identity. Upstream certificate verification is a separate responsibility of the proxy and its configured policy.

03

CA trust

Your app must trust the inspection certificate.

More details · about what you see

  • One destination, a different issuer

    The app receives an inspection certificate for the destination, signed by the workspace CA—not the original certificate presented by the remote server. That is why the app must trust this CA.

  • Install only where you need it

    Use Skewer’s CA Trust tab for supported browser profiles or system stores. Prefer a dedicated test profile or device. Trusting this CA permits its holder to issue certificates your app will accept.

  • Some apps have additional checks

    An app may use a private trust store or certificate pinning. Installing a system CA does not guarantee it will accept interception. This guide explains ordinary certificate trust, not how to bypass those protections.

04

Spider

Spider turns live traffic into something you can change.

More details · about what you see

  • Not another network hop

    Spider is an observer and controller connected to Smithproxy through callbacks and APIs. Your app is not configured to use Spider as its proxy. Smithproxy remains responsible for forwarding the connection.

  • Scripting is an active tool

    Spider’s payload workbench supports scripts that examine content and produce replacements. Applying a replacement to live traffic requires the relevant live-edit or inspection mode; a preview alone is not a change to the connection.

  • Keep edits deliberate

    Start with a small test request and one recognizable change. Content callbacks can be chunks rather than entire application messages. Editing bytes does not automatically preserve every protocol’s framing or semantics.

05

Sift

Sift asks: what do these bytes tell us?

More details · about what you see

  • A stream, not just one packet

    Sift tracks both directions of a flow. Recognition can depend on bytes arriving over multiple chunks and on the structure of the exchange, rather than a single packet or a familiar port.

  • Recognition is not decryption

    Sift identifies what the supplied data supports. TLS inspection can expose application content to it; encrypted traffic does not become plaintext merely because Sift receives it.

  • Separate analysis from action

    Sift returns findings. Those findings are distinct from forwarding, policy enforcement and a user’s content edits in Spider. Missing evidence should not be mistaken for a confident identification.

06

Lored

Lored adds context about the destination.

More details · about what you see

  • Two kinds of evidence

    Sift’s payload matches and Lored’s destination-based candidates are separate results. A hostname or IP association can add context, but it is not the same as proving an application from its bytes.

  • An optional enrichment path

    Sift queries Lored only when configured and enrichment is requested. Lored is not required to explain transparent proxying or TLS inspection. Its availability and data depend on the workspace setup.

  • Metadata, not a copy of the whole conversation

    The lookup uses destination information such as IP, port, SNI or HTTP host and protocol. Complete HTTP URLs are not forwarded by default. This is a context query, not an additional traffic-forwarding hop.

07

Together

One traffic path. Different jobs around it.

More details · about what you see

  • Follow the question you are asking

    How does it get there? Routing and Smithproxy. What does the content say? Sift. What is the destination associated with? Lored. What can I observe or change? Spider.

  • A map of responsibilities

    The diagram shows conceptual relationships, not a promise that every byte visits every tool or that callbacks always run in this order. Configuration controls inspection, enrichment and live edits.

  • Try it with one request

    Attach a test browser with Skewer, install the workspace CA into that profile, then visit a simple site. Open Spider from the signed-in Saslik portal and match the destination to the live session.
